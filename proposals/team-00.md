## Project Title

CI Triage Agent: classifying continuous integration failures and recommending the next action

## Abstract

Continuous integration pipelines at mid-size engineering organizations fail for
reasons that often have nothing to do with the code under review: a flaky test, an
expired credential, a transient network timeout, or a genuine regression. Engineers
spend hours each week reading logs to tell these cases apart, and the cost grows with
every test added. We propose CI Triage Agent, a multi-agent system that reads a
failed pipeline run and produces a labeled diagnosis with a recommended action.

The system uses four coordinating agents. A retrieval agent pulls the failing job
log, the diff under test, and the last thirty runs of the same job from the CI
provider API. A classification agent labels the failure as flaky, infrastructure,
dependency, or regression, citing the log lines that support the label. A history
agent checks whether the same test has failed on unrelated commits, which is the
strongest available signal of flakiness. A reporting agent writes a short pull
request comment and, for infrastructure failures, drafts the retry command.

Data comes from the public GitHub Actions logs of three large open source
repositories, roughly four thousand failed runs, of which we will hand label six
hundred as a held-out test set. Evaluation measures per-class accuracy, the false
regression rate, which matters most because a missed regression is expensive, and
median cost per triage in both tokens and dollars. We will compare a single-prompt
baseline against the multi-agent design to show whether the added structure earns
its cost.

The main risk is log volume, since one run can exceed model context limits. We plan
to address it with a chunked retrieval step that indexes the log and surfaces only
the failing region to the classification agent.
